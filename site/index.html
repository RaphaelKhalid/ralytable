Interpretability belongs in the type system.

Within a few years you will not be allowed to deploy a model you cannot explain, and almost nobody is building for that. Raly is a language whose types track what a vector represents — dimension, VSA family, superposition load, and which roles are bound into it — so the signature is a description of the model, readable without running it.

The thesis

Reverse engineering is stalling.

Trained networks have a thin layer of legible structure and a very long tail of junk heuristics. Every year that stays true, building models legible from the start gets more valuable.

Asking the model does not work.

We measured it. A reasoning model's self-reported dependency graph predicts its own measured causal importance worse than the position of the step in the trace does. Structure has to be built in, not requested.

So put it in the types.

Not a new architecture and not a probe. A compiler that refuses to build a representation it cannot describe — and a signature you can read instead of a weight matrix you cannot.

What the type system tracks

Four properties a tensor throws away.

In PyTorch a hypervector is a float32[1000]. So is every other hypervector, from every other family, over every other codebook, holding any number of items, carrying any set of roles. Raly's design makes all four of those part of the type, using four small decidable mechanisms rather than one big solver.

roles are static, values are runtime
// A role schema is a set of labels carried in the type.
// WHICH roles are bound is static. WHAT is bound to them is not.

fn encode(a: Sym, p: Sym) -> Vec<MAP<D=1000>, roles={agent, patient}>

// The signature is the documentation. You can read what this
// function represents without reading its body or its weights.

let s = encode(dog, ball);
let who = unbind(s, instrument);
//                  ^^^^^^^^^^ error: `instrument` is not in {agent, patient}
Mechanism: row polymorphism with scoped labels (Leijen). Duplicate labels are permitted, which is what you want — binding a role twice is meaningful in VSA, not an error. Errors name the missing label instead of printing a residual type.
load is counted, not hoped for
// Superposition load rides along in the type: "holds 3 of 31".

space Concepts = MAP<D=1000>;          // capacity 31, measured

let a: Vec<Concepts, load=1> = atom("dog");
let s: Vec<Concepts, load=3> = bundle(a, b, c);

for item in stream {          // 50 timesteps
    s = bundle(s, item);      // load grows in the type
}                                // -> RALY5001 at 32
Mechanism: natural-number load terms with interval bounds — a small abstract-interpretation lattice, not an arithmetic theory, with an explicit checked coercion where the checker cannot see through it. Futhark's compromise, for the same reason: a checked coercion with a good message beats a solver that sometimes answers.
Dimension & family

Free abelian group, not an assertion.

Dimensions unify as integer exponent vectors — Kennedy's units of measure, decidable, principal types preserved, shipped in F# since 2.0. VSA family is a finite enum under ordinary HM unification, with explicit coercions only. MAP<1024> and FHRR<1024> stop being the same type.

Not a novelty claim

These mechanisms are proven. That is the point.

Dex has typed index sets; Futhark has size types; F# has units. Compile-time shape and dimension checking is not new. What is missing is anyone shipping it in a tool ML practitioners actually use, extended to the things VSA needs — load and roles. That is an execution gap, not a novelty gap, and execution gaps are the ones you can close.

The bug this is for

Silent in PyTorch. Caught at compile time in Raly.

This is specifically a vector-symbolic failure, not a claim about neural networks in general. Bundling superposes items into one vector; past a capacity that scales linearly with dimension, retrieval decays toward chance. Nothing throws. The tensor is the right shape, the gradients flow, the loss goes down, and the retrieval is wrong.

silentbundle.py
import torch

D = 1000
codebook = torch.sign(torch.randn(1000, D))   # MAP atoms

scene = torch.zeros(D)
for i in item_ids:              # 34 of them
    scene += codebook[i]        # bundle
scene = torch.sign(scene)

# retrieval: nearest atoms to the bundle
top = (codebook @ scene).topk(len(item_ids)).indices

# No exception. No warning. Correct shapes throughout.
# At D=1000 the top-34 set is simply no longer the set
# you put in, and nothing in the program can tell you.
Measured on this exact protocol: at D=1000 over a 1000-atom codebook, top-N retrieval holds at ≥95% up to 31 items and falls away after. At D=256 the ceiling is 5.

The same shape of bug shows up in things people ship right now. Mean-pooling sentence embeddings is bundling. We measured that too: at 10 pooled all-MiniLM-L6-v2 sentence embeddings, the centroid returns two thirds of the wrong things — accuracy 0.354 against a random-vector baseline of 0.997 at equal dimension. No error, no signal.

Measured, before writing the language

Four results. Three of them are negative.

Every number below came out of this repository, on real data, with the script that produced it sitting next to it. Kill criteria were written before the runs. Nothing here is cited from a literature summary — where a summary and a measurement disagreed, the measurement won.

01 · claimed vs causal
|ρ| ≤ 0.09 vs ρ = −0.45 for position alone

A model's account of its own reasoning is not the causal graph.

Thought Anchors' released rollouts carry both an LLM judge's depends_on graph and resampling-measured counterfactual importance, and nobody had ever checked one against the other. Across 6,955 chunks from 40 traces and 2 models, every graph-derived predictor correlates with measured importance at |ρ| ≤ 0.09, while raw position correlates at −0.45. The graph is a worse predictor of causal importance than where the step happened to sit.

03 · position decay
−0.551 → +0.009 conditioned on q ∈ [0.3, 0.7]

Importance decays with depth because models commit early.

The obvious reading of a −0.551 position/importance correlation is a runway artifact. It is not. Restrict to chunks where the answer is still genuinely open and the correlation collapses to +0.009, CI [−0.126, +0.144]. Position predicts importance only because position predicts how decided the answer already is. The rest of the trace is follow-through.

04 · capacity
31 items at D=1000, not the ~10 a summary suggested

The capacity number in the type had to be measured.

M* = Θ(D / ln N) is solid; the constant is what a compile-time check actually needs, and published constants vary by ±2×. Measured over random bipolar codebooks at 95% top-N retrieval: 5 items at D=256, 15 at D=512, 31 at D=1000, 67 at D=2048 — and 22 rather than 31 when the codebook grows to 10,000 atoms. Linear in D, logarithmic in vocabulary, exactly as the theory says, at roughly 3× the constant the summary implied.

3–5× worse than the matched random baseline

Real embeddings lose bundled items faster than the toy predicts.

Mean-pooled MiniLM sentence embeddings over 7,600 AG News headlines: 0.354 retrieval at N=10 against 0.997 for random Gaussian vectors at the same D=384. Averaged token embeddings collapse almost immediately and converge on a fixed set of hub sentences regardless of the query. What works today

A lexer and a diagnostics engine. That is the entire compiler.

Nothing on the "not built" list is stubbed, faked, or half-written. It is absent. This section exists because a project pitched on catching what other tools hide should not begin by hiding what it has not built.

The diagnostics crate was built first and treated as the product rather than as plumbing. Raly's whole pitch is catching mistakes other languages let through silently, so what a user reads when something is wrong is the deliverable.

  • ✓raly-diag — byte-offset spans, a source map that derives line/column only at render time, primary ^ and secondary - labels, separate note: and help: channels, stable greppable codes. Hand-written renderer, no dependencies, output asserted character-for-character.
  • ✓raly-lexer — logos-based, and total: every input including arbitrary bytes yields a token stream and never panics. Four recoverable error classes with targeted homoglyph hints. Comments kept as trivia.
  • ✓raly-ast — arena-allocated, 32-bit ids, interned names, generic visitor. Explicitly provisional: no precedence and no keyword meaning is encoded, so none could be smuggled in under cover of scaffolding.
  • ✓raly — a binary with lex and check, honest exit codes, 71 passing tests, zero clippy warnings.
  • ·Parser — in progress. No grammar, no precedence table. raly check stops after lexing.
  • ·Type system — does not exist. No types, no inference, no checking. Everything on this page under "designed" lives here.
  • ·Name resolution, IR, codegen — do not exist. raly cannot produce an executable and does not pretend to.
  • ·The model — does not exist. Ralytable-1 is Phase 3.
  • ·Keyword semantics — space, bind, bundle, permute, unbind, cleanup lex to distinct tokens and mean nothing yet. Reserving them is the only commitment made.

The phases

Every phase has a gate, and a gate is a number that can fail.

Not a milestone to walk past. Where a gate fails, the phase is a negative result and it ships as one.

Phase 0 · mostly done

Foundations

Write the semantics down before the compiler assumes them: which VSA algebraic laws actually hold, capacity measured rather than cited, prior art surveyed, architecture decisions researched before they get expensive to change. The compiler skeleton is the open item.

GateNo claim in the semantics doc that isn't measured or cited. Holding; one asserted claim already got caught and corrected.
Phase 1 · current

The language runs

Grammar, parser, typechecker. Capacity types, role-schema types, static nesting-depth checks that force a cleanup before retrieval degrades. Differentiable end to end. Error messages good enough to be the reason people use it.

GateOne VSA experiment visibly easier in Raly than in fifty lines of jax.numpy. If that can't be produced, the language is a cathedral and it stops.
Phase 2

The legibility curve

Train the same task across dense, weight-sparse, discrete-bottleneck, VSA-structured and gate-based models, and measure both how good each one is and how much of it a person or an auditing model can actually recover. The hard part is a legibility metric defined independently of the architecture — one that measures whether the algorithm can be recovered, not whether the weights are discrete.

GateNone: this one can't fail, only inform. A cheap tax means the direction is live; an expensive one is a real negative result that saves other people a wall.
Phase 3

Ralytable-1

Small, local, legible. A small alphabet the model's entire internal vocabulary can be listed from. Soft perception, hard reasoning: a neural encoder into a discrete readable core. Distilled from a cheap teacher, training on one 8GB laptop GPU.

GateThe reasoning core is readable and the model isn't useless. Both, or the thesis is wrong and it gets said out loud.
Phase 4 · the strongest idea

Legible RLHF: grade the reasoning, not just the answer.

RLHF rewards outcomes because outcomes are all a reward model can see. The reasoning that produced the answer is opaque, so it goes ungraded — and that is exactly how you train a model to reach right answers through broken reasoning.

If the reasoning core is legible, the reward model can see inside it. You grade the process instead of the product: penalise a right answer that came out of a derivation that doesn't hold, reward a sound step that happened to land wrong. A dense transformer cannot do this, because there is no readable process to grade. This architecture can.

That would make it the first case we know of where being interpretable makes a model better rather than merely safer — which flips interpretability from a tax into an advantage.

GateProcess-supervised beats outcome-supervised on held-out reasoning at equal compute. If legibility doesn't buy capability here, it probably never will — and that is still worth knowing.
Phase 5

Scale

Does the legibility tax shrink with scale or grow? Raly as infrastructure other people build on, and the obvious default when interpretability stops being optional.

GateOpen.

What could kill this

Four ways this is wrong, written down in advance.

Risk 01

The legibility tax may be fundamental.

ETH Zürich's recurrent differentiable logic-gate networks reached 4.39 BLEU at inference on WMT'14 En–De. That is near the floor. It kills the maximalist all-discrete version outright and leaves the version worth testing: soft perception with a hard reasoning core. Phase 2 exists to find out which before betting on it.

Risk 02

Learned codebooks may void every capacity guarantee.

VSA capacity bounds hold because atoms stay near-orthogonal. Gradient descent has no reason to keep them that way, and no published method gives a training-time guarantee. This gates the entire learnable-VSA premise, and the load type depends on it.

Risk 03

Discrete does not mean legible. Small means legible.

Convolutional logic-gate networks hit 86.29% on CIFAR-10 using 61 million gates. A 61M-gate circuit is exactly as opaque as 61M weights. Any legibility metric has to measure recovery, not discreteness.

Risk 04

DSLs die from missing on-ramps, not bad design.

This is the ordinary way a language like this fails, and it is why Phase 1's gate is about a task being visibly easier rather than about the type system being elegant.

Prior art was surveyed properly, and the honest answer came back narrower than hoped. HPVM-HDC is a real VSA compiler. GHRR already swapped transformer attention for VSA binding. Concept bottleneck LLMs, weight-sparse transformers and KANs are all interpretable-by-construction already. The claim here is narrower and more specific: interpretability living in the type system, and a legibility/capability curve measured across architecture families rather than inside one.
