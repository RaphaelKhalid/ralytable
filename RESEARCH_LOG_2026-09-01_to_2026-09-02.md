## Loop 02 — typed program ledger probe

Status: complete.

- Question: under a small explicit-state budget, does a typed program ledger
  preserve bindings and causal edits better than a flat sketch or slot state?
- Prior art: Slot Attention supplies competitive binding; neural module
  networks supply executable composition; Perceiver IO supplies a learned
  latent bottleneck. The proposed difference is a content-addressed typed
  program ledger with explicit dataflow edges and deterministic execution.
- Null: a flat fixed-capacity sketch.
- Alternatives: entity slots, typed program graph, typed program ledger.
- Primary endpoint: exact typed-graph recovery on held-out synthetic linear and
  branch/merge programs.
- Secondary endpoints: permutation invariance, relevant counterfactual change,
  irrelevant placebo preservation, recovery by graph shape/depth, parameter
  budget, and audit surface.
- Limitation: exact facts are supplied to the representations; this is not a
  learned parsing or coding result.
- Result: across five seeds and 600 tasks per architecture, the flat sketch
  recovered 13.2%, entity slots 37.5%, typed program graph 100%, and typed
  program ledger 100%. Relevant counterfactual change and placebo preservation
  were both 100% for the graph and ledger, while slots reached 37.5% and the
  flat sketch 0% placebo preservation.
- Decision: keep explicit typed dataflow edges as the substrate baseline. Do
  not claim content-addressed ledgers are better than typed graphs; their
  hypothesized benefits were not exercised by this task family.
- Validity: exploratory representational result only. Exact typed facts were
  supplied, so no learned parser, code generator, benchmark, Qwen comparison,
  or end-to-end interpretability claim was tested.

## Loop 29 — semantic ID normalization and collisions

Status: complete.

## Loop 30 — dependency-aware incremental cache

Status: complete.

## Loop 31 — deterministic parallel scheduling

Status: complete.

- Result: all schedulers produced valid topological schedules and honored the

## Loop 32 — transactional speculative execution

Status: complete.

- Question: can bounded candidate search avoid leaking side effects from a
  branch invalidated by a later proof check?
- Result: the transactional ledger passed candidate selection/reordering,
  late-failure isolation, all-invalid isolation, and invalid high-score
  placebo isolation 5/5 each across five seeds. Eager execution leaked both
  invalid and valid effects. An undo log removed invalid memory state but leaked
  irreversible `email_bad` effects and failed every case.
- Decision: isolate speculation and commit effects only after proof validation;
  compensating logs are not sufficient for external effects.

## Loop 34 — selective verifier abstention

Status: complete.

- Question: should a compact coder emit code solely on confidence, or abstain
  until proof and verifier checks pass?
- Result: base confidence-only emission covered 6/8 with risk 0.50 and emitted

  five seeds and three variants, average risk was 0.4444, 0.1667, and 0.0;

- Decision: make abstention first-class; reserve high-confidence emission for
  candidates passing proof and verifier gates.
- Limitation: fixed synthetic batch, not calibration data or a coding

## Loop 35 — calibration drift under distribution shift

Status: complete.

- Question: does a source-calibrated confidence threshold remain safe on a
  shifted coding distribution?
- Result: source calibration selected threshold 92 for a 10% risk target. On
  source data, fixed 80% confidence had coverage 0.60/risk 0.3333, while the
  calibrated threshold had coverage 0.20/risk 0.0. Under shift, fixed 80% risk
  rose to 0.5714 and the calibrated threshold rose to 1.0. A separate
  proof-plus-verifier gate emitted zero shifted candidates and retained zero
  observed risk at zero coverage.
- Decision: confidence is not a guarantee under shift; expose drift and allow
  explicit verifier-gated abstention, including zero-coverage outcomes.
- Limitation: handcrafted distribution shift, not calibration data or a coding
