A compiler that knows what a vector holds.

Machine learning tools see a as a list of numbers and check that the lengths match. They cannot see that the list is a bag that holds thirty-one things and already has seven in it. Put a thirty-second one in and nothing throws, nothing crashes, and the model quietly gets worse.

Raly puts the count in the type. Overfill the bag and the program does not compile.

Type into the box. The compiler answers.

This is the compiler's front door, built to and running inside this page. Nothing is sent anywhere. Edit the code and the errors redraw on every keystroke, squiggles under the exact characters at fault, click a message to jump to it.

This build carries the whole front end: the part that reads characters, the parser, the part that resolves names, and the type checker, plus the part that draws errors. It calls the same function the command line calls, which is why the carets line up identically. The file it opens with is the capacity error, and you can fix it in place: drop one item from the bundle and the error goes away as you type.

What it catches

Forty things into a bag that holds thirty-one.

Adding vectors together is how these systems store several things in one place. There is a hard limit on how many, and past it you can still read something out; it is just the wrong thing. No exception, no crash, correct shapes throughout. The accuracy falls and the code looks fine.

Raly counts. The compiler knows the bag holds thirty-one because we measured thirty-one, and it prints the number, where it came from, and the width you would need instead.

The block on the right is copied from compiler/crates/raly/tests/ui/capacity-exceeded.stderr, which is checked character for character on every build. The playground above prints the same thing, from the same code: it is the file it opens with.

The annotation

One line that says what a vector is carrying.

Vec[Concepts; load 3; roles {Subject, Verb, Object}]
  • ConceptsWhich space this vector belongs to. That fixes its width and its family, so vectors from a different space cannot be mixed in by accident.
  • load 3How full it is. Three things are in the bag, and the compiler knows the bag's limit, so it can tell you when a fourth will not fit.
  • roles {…}Which slots are filled is fixed at compile time. What goes in each slot is decided when the program runs.

The second half is the reason this is a language and not a library. If the type lists the slots, then the signature of a function tells you what it represents, and you can read that without running the model, training a probe, or digging through weights.

Two things this is not. Checking dimensions at compile time is not new; Dex, Futhark and F# have done it for years, and our claim is narrower, that no machine learning tool people actually use has checks like these. Building models that explain themselves is not a new field either; concept bottleneck models, weight-sparse transformers and KANs all exist. What is unusual here is putting the explanation in the .

How it works

Four passes, one run, every error at once.

raly check runs every pass every time. No pass is allowed to stop the next one, so a typo does not hide an unknown name and an unknown name does not hide a capacity error. You get the whole list on the first try.

sourcea .raly file
→
lexany bytes at all become tokens, and it never panics
→
parsehand-written, recovers from bad syntax, covers the whole file
→
resolveworks out which definition every name points at
→
typecheckfour properties, four small solvers

width tracked as a unit of measure, so a mismatch prints the leftover ratio instead of the words "unification failed"
family is a short fixed list, so MAP[1024] and FHRR[1024] stop being the same type
how full is a range of whole numbers over measured capacity: bundle adds, bind multiplies, cleanup drops back to one
slots use , so taking out a slot the vector never had is a compile error

Measured, not cited

The numbers the compiler prints came out of experiments in this repository.

We wrote down what would count as failure before each run, reported every result next to what you would get with no model at all, and re-derived each headline number a second way. Some of the results are negative and they ship the same as the rest.

04 · capacity

Thirty-one items at width 1000.

Retrieval holds above 95% up to thirty-one items bundled into one vector of width 1000, roughly three times what a literature summary implied. Four widths measured, and this is the number the compiler prints.

experiments/04 →
07 · retrieval cost

Averaging passages into one vector costs a quarter of search accuracy.

On a standard search benchmark, mean-pooling eight passages into a single document vector drops the hit-rate from 0.877 to 0.619 with topically coherent groups. About 76% of that loss is the averaging itself, isolated with a max-scoring control. A model with twice the width paid the same cost.

experiments/07 →
06 · discrete core

Legibility costs about three points of accuracy.

Forcing the middle of the model through 1024 fixed symbols moved top-1 accuracy from 0.8383 to 0.8065 at matched parameters, and made the model less surprised by its own text, not more. Bigger alphabets got more capable and more legible together, which is the opposite of what we expected.

experiments/06 →
01 · claimed vs causal

A model's account of its own reasoning is not the causal graph.

Across 6,955 steps, the dependency graph a model writes out correlates with what actually mattered at +0.203, and at +0.015 once you account for how far into the answer each step sits. Position alone gets -0.551. Structure has to be built in, not asked for.

What the 1024 symbols bought, against every control we could think of

We measured how well a symbol predicts whether the character it fired on belongs to a premise, a working step, or the answer. Three ways of guessing, on the same text:

So the symbols beat the raw character by +0.033. That is the number, and it is real, because a symbol sees context and can tell the same character apart in a premise and in a working step. Reproduce it with experiments/06_discrete_core/leakage.py.

What exists

The front end is finished. The back end is not started.

Nothing on the second list is stubbed or half-written. It is absent.

  • ✓Errors that point at exact byte ranges, with a primary and secondary location, separate note and help lines, and stable codes you can grep for. The text is asserted character for character.
  • ✓Lexer that turns any input at all, including arbitrary bytes, into tokens without panicking.
  • ✓Parser written by hand, recovers from bad syntax, and produces a tree that covers the whole file.
  • ✓Name resolution with two namespaces and proper scopes. Using a name before it is defined gets its own message. Suggestions stay quiet unless they are confident.
  • ✓Type checking for all four properties: width, family, how full, and which slots. 179 tests, zero warnings.
  • ✓Browser playground: the whole front end as 286KB of WebAssembly, the capacity error live, no install.
  • ·Code generation does not exist. raly checks programs; it cannot run them.
  • ·Ralytable itself is not built. What exists is the 6.4M-parameter model the second demo takes apart.

Limits, stated once

  • The model in the second demo cannot reason. It is 6.4M parameters trained for six minutes on 4,042 synthetic word problems. It writes correctly formatted arithmetic nonsense. The demo is about seeing what it is doing, not about what it can do.
  • One seed per configuration, one corpus, one teacher. There are no error bars on finding 06.
  • That corpus is synthetic and formulaic, which almost certainly makes its structure easier to encode than real text would be.
  • The capacity numbers come from random codebooks. A codebook learned by gradient descent has no pressure to stay spread out, and whether the numbers survive training is the open question that gates the whole idea.
  • Findings 05 and 07 cover four small encoders on three datasets, all English, all short passages, all mean pooling. They are claims about those models on that data.
  • Nothing here runs. There is no code generator, so Raly programs type-check and stop.

All of it is in the open, including the parts that did not work.
